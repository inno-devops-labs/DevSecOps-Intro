# Five-minute walkthrough

I built a small DevSecOps program around OWASP Juice Shop rather than treating the labs as separate tool demos. The flow starts with getting the application running in a repeatable way, then adds controls at the points where risk enters: secrets before commit, signed commits, dependency visibility, code scanning, dynamic testing, infrastructure scanning, container hardening, artifact signing, runtime detection, and finally DefectDojo as the place where the findings become a managed backlog.

The first lesson was that every scanner sees a different slice of the same system. In Lab 4, Syft gave me the SBOM and Grype/Trivy turned it into dependency and image findings. That was useful, but it was also noisy: a vulnerable package in the image is not automatically the most urgent thing if the code path is unreachable or there is no fix. Lab 5 gave more concrete evidence because Semgrep looked at the source and ZAP attacked the running application. Lab 6 showed how infrastructure mistakes create risk before the app even starts. Lab 7 made the container harder to abuse. Labs 8 and 9 added the controls that do not look like normal vulnerability findings: signed artifacts, attestations, policy-as-code, and Falco runtime alerts.

The specific finding I would trace is SQL injection. Semgrep reported `javascript.sequelize.security.audit.sequelize-injection-express.express-sequelize-injection` in `routes/search.ts` and `routes/login.ts`, where untrusted input reaches Sequelize queries. ZAP then confirmed the same class of issue dynamically: the authenticated scan reported SQL Injection against `/rest/products/search` with server error evidence. That combination changes the priority. A SAST-only result could be a false positive, and a DAST-only result could lack enough source context to fix quickly, but together they point to a real bug, a reachable endpoint, and a clear remediation path: replace string-built SQL with parameterized queries, rerun Semgrep, rerun the ZAP authenticated scan, and only close the DefectDojo finding when both sides agree.

One thing that did not work cleanly was the DefectDojo import itself. The lab maps `auth-report.json` to the `ZAP Scan` parser, but DefectDojo 2.58.3 rejected the JSON report and asked for XML. I did not ignore the DAST result or invent a count; I converted the same ZAP JSON data into the traditional ZAP XML shape and imported the same 13 alerts. Another small trap was `trivy-k8s.json`: it imported through `Trivy Operator Scan`, but produced 0 findings because the file shape was not the Trivy Operator CRD format. That is a useful operational lesson: an HTTP 201 import response does not prove the data became useful findings.

The number I would put on a slide is **581 active findings, but only after source context**. On its own, 581 sounds like a fire. Broken down, it becomes a program: 36 Critical, 253 High, 233 Medium, 46 Low, and 13 Info; 568 SLA-scoped findings were inside SLA immediately after import because the import date was today, while the 13 Info findings had no SLA clock. The more important slide note is that the raw number mixes real application bugs, duplicate or overlapping image findings, deliberately vulnerable IaC fixtures, and control evidence that does not appear in DefectDojo at all.

My priority would be to fix the SQL injection first, then rebuild the image and triage the Critical dependency findings with fix availability. I would not let the large IaC fixture count drive the sprint unless those files were actually headed to production. For Labs 8 and 9, I would not force everything into a vulnerability dashboard: cosign verification should stay a CI gate, while Falco alerts and Conftest failures should become generic findings only when they need an owner and a deadline.

The outcome is not "I ran ten tools." The outcome is a defensible workflow: evidence comes from multiple layers, findings are deduplicated by location and component, deadlines are explicit, risk acceptance has an expiry, and the next action is clear enough for a manager and a developer to agree on.
