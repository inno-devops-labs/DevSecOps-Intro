# Lab 10 Bonus — The five-minute walkthrough

*("Tell me about a security project you've worked on.")*

Over a semester-long DevSecOps course, I took a single deliberately-vulnerable application — OWASP Juice Shop — and built out the security tooling you'd expect around a real service: dependency scanning, SAST, DAST, infrastructure-as-code scanning, container and Kubernetes hardening, supply-chain signing, and runtime detection. The point wasn't to collect eleven tools for a resume line — it was to see what each one actually catches that the others miss, and then to put all nine weeks of output into one system so it stops being nine separate spreadsheets nobody reads.

Let me walk through one finding I traced end to end. In the DAST lab, I ran an authenticated OWASP ZAP scan against Juice Shop and it flagged a High-severity SQL Injection alert on the product search endpoint — `GET /rest/products/search?q=...`. ZAP's evidence was a raw HTTP 500 when it threw a single quote into the query parameter. That's a strong signal but not proof by itself — a 500 could just be a crash, not an injectable query. So I went to the source: Juice Shop constructs that search query with string concatenation instead of a parameterized query, which is exactly the kind of thing Semgrep's static analysis flagged independently in the same lab, on the same file, as an ERROR-severity finding for unsanitized query construction. Two different tools, two different vantage points — one testing the running app from outside, one reading the source from inside — converging on the same root cause. That's the finding I'd act on first if this were a real triage queue, and it's exactly the kind of correlation that later became the point of the whole capstone: a scanner alert alone is a data point, but a scanner alert that another tool independently confirms from a different angle is something you can actually prioritize with confidence.

Now, the thing that didn't work. When I tried to import that ZAP scan's JSON report into DefectDojo — the vulnerability-management platform I stood up for the capstone — the import failed outright with an HTTP 400 and a cryptic "wrong file format, use xml" error. The lab's own instructions said to import the JSON report; DefectDojo's own parser table lists "ZAP Scan" as accepting it. I could have just shrugged and skipped that report, eaten the missing data, and moved on — plenty of people would have. Instead I went and read DefectDojo's actual parser source code, not just its docs, and found the ZAP parser hard-checks the file extension for `.xml` and only understands ZAP's XML report schema — the JSON format, while equally official, was never supported by that importer at all. Rather than re-running the whole scan just to get an XML file, I wrote a small conversion script that re-serialized the exact same alert data — same titles, same CWEs, same evidence — from the JSON structure into the XML structure the parser expected, and imported that instead. Same thirteen findings, zero data lost, just a different envelope. I hit essentially the identical problem a second time with the Kubernetes Trivy scan: the lab said to import it as "Trivy Operator Scan," but that parser expects the schema a live Kubernetes operator produces, not the plain CLI JSON `trivy k8s` actually outputs — it silently accepted the file and reported zero findings, no error, nothing. I only caught that because I checked the finding count against what I could independently verify was in the raw file. The fix was realizing the plain "Trivy Scan" parser already has a code path for that exact CLI schema. Both of those taught me the same lesson: when an integration silently does the wrong thing, "it imported without an error" is not the same as "it worked," and the fastest way to find out which one you got is to go read the fifty lines of parser code instead of trusting the mapping table.

If I had to put one number on a slide, it's this: **645 active findings, but roughly 79% of them are three overlapping dependency scans of the same base container image** — meaning the real, de-duplicated risk surface is a fraction of that headline count, and the number that actually matters isn't "how many findings exist" but "how many distinct problems exist, and which ones are new since last week." That's the number I'd want on a dashboard, not the raw count, because the raw count rewards scanning the same thing three times and punishes nothing.
