# 5-Minute DevSecOps Program Walkthrough — OWASP Juice Shop

## (0:00–0:30) Context

For this project I built a complete DevSecOps security program around OWASP Juice Shop, covering the application lifecycle from source code to runtime monitoring. The pipeline includes secret scanning, software composition analysis, static analysis, infrastructure scanning, image signing, policy enforcement, runtime detection, and centralized vulnerability management using DefectDojo.

---

## (0:30–2:00) Layers

The pipeline starts before the code reaches the repository.

At the **pre-commit** stage I used **gitleaks** to prevent accidental secret leakage and configured **SSH-signed Git commits** to guarantee commit authenticity.

During the **build** stage I generated an SBOM using **Syft**, scanned third-party dependencies with **Grype**, and performed static application security testing with **Semgrep**.

Before deployment I validated infrastructure using **Checkov** and **KICS**, signed container images with **Cosign**, and enforced Kubernetes security policies using **Conftest** together with the Restricted Pod Security Standard.

At **runtime**, I configured **Falco** to monitor Kubernetes activity through eBPF and detect suspicious behavior after deployment.

Finally, all security findings from previous labs were imported into **DefectDojo**, where they were aggregated, deduplicated, prioritized using an SLA policy, and tracked through remediation metrics such as MTTR and vulnerability age.

---

## (2:00–3:00) Findings + Closures

Across all imported scans, DefectDojo received **456 raw findings**, which were reduced to **310 unique findings** after deduplication.

The final active backlog consisted of **305 findings**, including **11 Critical** and **120 High** severity issues.

During this reporting period I mitigated **three Critical dependency findings**.

I also created a formal Risk Acceptance for **GHSA-pxg6-pf52-xh8x** affecting **cookie 0.4.2**. It was accepted because the vulnerable code path is not reachable in the current Juice Shop configuration, and the acceptance expires on **10 October 2026**.

A good example of correlation is **CVE-2023-46233**. It appeared in several Trivy scans, including the SBOM, container image, and Kubernetes scan. DefectDojo automatically deduplicated these reports into a single finding with ID **447**, making remediation much easier.

## (3:00–4:00) Metrics

The current **MTTR** is approximately **0 days** because the mitigated findings were closed immediately after import. Although this is only a demonstration dataset, it is consistent with the workflow expected from an automated security pipeline. For comparison, DORA Elite organizations also aim for remediation in less than one day.

The median vulnerability age is also **0 days** because all findings were imported during the same reporting period.

Current **SLA compliance** is **100%**, since every finding is still within its configured remediation window.

The vulnerability backlog currently contains **310 unique findings**, which establishes the baseline for measuring future trends. As more scans are imported over time, this baseline can be used to monitor whether the backlog is growing or decreasing.

## (4:00–4:30) Next Steps

If I had another quarter, I would improve **Defect Management** according to the OWASP SAMM maturity model.

My priority would be implementing cross-parser deduplication so that identical vulnerabilities reported by different scanners, such as Grype and Trivy, are merged into a single finding. I would also integrate Falco runtime alerts directly into DefectDojo to provide continuous operational visibility alongside build-time scanning.

## (4:30–5:00) Q&A Anticipation

### 1. How would you handle a Log4Shell scenario?

The first step would be checking the project's SBOM generated by Syft to quickly identify every affected Log4j component and its version. After locating vulnerable dependencies, I would use Grype and Trivy to verify exposure, update the affected packages, rebuild and sign the container image with Cosign, rerun all security scans, and finally import the new results into DefectDojo to confirm the vulnerability was fully remediated and closed.

### 2. Why didn't you use IAST or commercial security tools?

The objective of this project was to build a complete security pipeline using open-source technologies that can be reproduced without licensing costs. Tools such as Semgrep, Grype, Checkov, KICS, Falco, and DefectDojo cover the essential stages of a modern DevSecOps workflow. Commercial or IAST solutions could improve runtime analysis and reduce false positives, but the architecture of the pipeline allows those tools to be integrated later without changing the overall process.
