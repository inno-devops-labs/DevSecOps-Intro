# Lab 10 Walkthrough — Five-Minute Security Project Script

This project built a small DevSecOps security program around OWASP Juice Shop. The goal was to connect tool results into decisions a team could act on. Across the labs, the work deployed the application, inspected its exposed surface, created a threat model, configured secure Git practices, generated SBOMs, scanned dependencies, ran SAST and DAST, checked infrastructure as code, hardened a Kubernetes deployment, signed artifacts, attached attestations, wrote runtime detection rules, and loaded scanner output into DefectDojo for vulnerability management.

The main slide number is **616 active findings** imported into DefectDojo for the Juice Shop product. That number is useful, but it is not the whole story. The same dashboard also showed **37 Critical** and **258 High** active findings, and those findings should drive the first remediation plan. The point of DefectDojo here was to turn many separate lab outputs into one backlog with severity, source tool, SLA, and ownership decisions.

One finding traced through the project was SQL injection. In the SAST phase, Semgrep reported `express-sequelize-injection` in routes such as `routes/login.ts:34` and `routes/search.ts:23`. In the DAST phase, ZAP reported SQL Injection against the login and product search endpoints after sending SQL-like input and receiving abnormal server responses. That correlation matters because the two tools are looking at the problem from different angles: Semgrep shows the unsafe source pattern, and ZAP shows suspicious runtime behavior. This finding should be first in the remediation queue because it is easier to explain and harder to dismiss than a finding from only one scanner.

The decision attached to that finding is also clear. The application should stop building SQL with user-controlled strings and use parameterized queries instead. That separates the SQL structure from user input, so characters from the request are treated as data rather than executable SQL. The work should be assigned to the application owner and kept on a short SLA because this is an application vulnerability with a direct request path.

One import issue was parser format compatibility. The ZAP evidence from Lab 5 was saved as JSON, while the DefectDojo 2.58.3 `ZAP Scan` parser expects XML. The same alert data was imported in the parser format DefectDojo accepts, then verified through the API. The lesson is that a vulnerability-management platform is only as reliable as the mapping between tool output and parser format; parser compatibility needs to be checked before a team trusts the dashboard.

The final management decision was to make the dashboard behave like a program, not just a report archive. The default SLA changed from 7/30/90/120 days to 1/7/30/90 days for Critical, High, Medium, and Low. That makes Critical findings a next-day response item and High findings part of the weekly remediation cycle. Median age, oldest age, and SLA compliance were calculated from the active findings, showing that the imported findings were new in this DefectDojo instance and that 603 of 616 active findings were currently inside SLA.

The biggest limitation is that not every security control becomes a scanner finding. Labs 8 and 9 produced signing, attestation, runtime detection, and policy-as-code evidence, but those do not appear automatically in DefectDojo through the parsers used in this lab. Those controls should be tracked as manual control evidence linked to the same product, because release readiness depends on both vulnerability findings and control evidence.

The project also showed why a security program needs both technical and management views. Scanner output is useful for engineers, but managers need severity, owner, SLA, exception status, and the reason a finding matters. A useful report therefore connects each major tool result to a decision: fix now, accept temporarily with a date, monitor until a fix exists, or track as control evidence outside the scanner dashboard. The manager summary is: the project has a measurable vulnerability backlog, SQL injection is the first application risk to fix, and the next step is assigning owners and dates instead of running more tools.
