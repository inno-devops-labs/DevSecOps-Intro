# Five-minute walkthrough — "Tell me about a security project you've worked on"

Over a semester I ran a full DevSecOps pipeline against OWASP Juice Shop — a deliberately vulnerable web app — and, more importantly, turned nine weeks of scanner output into something a team could actually act on. I want to tell you less about the tools and more about one decision, one finding I chased end to end, and one thing that broke.

**What I built.** I treated one container image as the artifact and attacked it from every angle a real pipeline would. I generated a software bill of materials and scanned it for vulnerable dependencies (Grype, Trivy). I scanned the source for injection and secrets (Semgrep) and ran the app under a DAST proxy, both unauthenticated and logged in (ZAP). I scanned the infrastructure-as-code that would deploy it (Checkov, KICS). I ran the app in Kubernetes under the strictest Pod Security Standard, pinned by digest, non-root, read-only root filesystem, with a default-deny network policy. I signed the image and attached the SBOM as a verifiable attestation (Cosign), so a consumer could prove what they were running. I watched it at runtime from the kernel with Falco and wrote a rule for cryptomining, and I enforced the same hardening rules *before* deploy with policy-as-code (Conftest). Finally I loaded every scanner's output into one vulnerability-management system (DefectDojo) and put deadlines on it.

Each of those was a choice, not a checkbox. For example, I chose digest-pinning enforced in CI over hoping people pin by hand, because a tag is mutable and I'd already proven that — I overwrote a signed image's tag with a different image and watched signature verification catch it. Prevention in the pipeline beats detection after the fact for anything you can check up front.

**One finding, traced end to end.** The strongest result was a SQL injection that two independent tools agreed on. Semgrep flagged `routes/login.ts` line 34 statically: the login handler built its SQL query by string-concatenating `req.body.email` straight into a `SELECT ... WHERE email = '...'`. Separately, ZAP's active scanner confirmed it dynamically against the running app by injecting a single quote into the email field on `POST /rest/user/login` and getting a database error back. Same bug, reached two different ways — static code and live traffic — which is exactly the finding you trust, because it is not a tool artifact. The fix I'd open a PR for is to stop concatenating and use a parameterized query with bind replacements, or the ORM's own finder. In DefectDojo that one issue is unambiguous; the noise around it is what took judgment.

**One thing that didn't work.** When I stood up DefectDojo — six containers — and tried to also run an authenticated ZAP active scan and the app at the same time, Docker's daemon ran out of headroom and hung completely: even `docker version` stopped responding. I'd overloaded the host. What I did about it: I restarted the Docker engine, confirmed DefectDojo's data survived because it lives in a database volume, and then deliberately *didn't* re-run the heavy active scan. Instead I ran the lighter passive ZAP baseline to produce the report I needed in about 80 seconds, imported it, and moved on. The lesson I took is operational, not security: know which of your containers hold state and which are disposable, and don't schedule your heaviest job next to your most important one.

**The number I'd put on a slide.** 580 active findings across the whole project — and the point of the slide is that the number is a trap. Roughly half of it is the same image counted twice by two different dependency scanners, plus a large block of deliberately-broken teaching infrastructure that never deploys anywhere. The real risk is small and specific: a handful of Critical dependency CVEs in the running image that already have released fixes — `jsonwebtoken`, `lodash`, `crypto-js`, `tar` — and the one SQL injection. So the slide says "580 findings, but the work this sprint is five of them," and underneath, the governance I set: Critical fixed in 3 days, High in 14, everything tracked against an SLA with an owner and an expiry date on anything we consciously accept.

That is the project: not that I ran ten tools, but that I can tell you which five findings matter, why, and when they'll be closed.
