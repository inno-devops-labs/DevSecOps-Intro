# A Security Project I Worked On — Five-Minute Walkthrough

Over one semester I took a single deliberately vulnerable web application, OWASP Juice Shop, through the whole lifecycle a real service goes through: threat model, source code, dependencies, infrastructure code, container, cluster, supply chain, runtime and finally a vulnerability management program. Each stage fed the next, so it became one pipeline, not ten exercises.

I threat-modelled the app before adding any scanner. I made the repository refuse to commit secrets, and I checked that the guard actually worked. When I later generated a signing key, gitleaks blocked it, but the standard private-key hook let it through because it doesn't know the Sigstore key header. Untested, I would have trusted a broken control.

For dependencies I generated an SBOM and scanned it with two tools. They disagreed usefully. One found a vulnerability in the Node.js runtime binary itself, and the other filed the same flaw under a different identifier. I later attached that SBOM to the image as a signed attestation, so after the next Log4Shell I can ask which images contain the package and trust the answer.

Here is the finding I traced end to end. Static analysis flagged a string-built SQL query in the login route. Static rules are often false positives, so I ran an authenticated dynamic scan, and it sent a single quote in the email field of the real login request and got a server error back. Two independent tools now pointed at the same line, and the classic payload `' or 1=1--` logs in as admin. The fix is bound query parameters instead of string interpolation, and the acceptance test is the same dynamic scan returning no error. It was the only finding with both a code location and a working request behind it, so it went to the top.

For the platform, I scanned the container image, then deployed it in Kubernetes under the strictest Pod Security profile. The image already ran as a non-root user, but the admission controller still rejected my first deployment until the security settings were explicit. Then I made the root filesystem read-only. The app crashed, because it writes into directories that also contain files it ships with, so an empty volume hid its own frontend. I listed every path it actually wrote to, and an init container copies the shipped content into writable volumes before start-up. The pod came up with a read-only root filesystem and served traffic, and the scanner's misconfiguration count went to zero.

I signed the image by digest and showed that a different image pushed under the same tag fails verification. I wrote runtime rules: one for writes to temporary directories, and a cryptominer rule that fires on a refused connection, because it watches the system call, not the network.

Something that didn't work: I initially loaded all the scanner output into DefectDojo and got the wrong version without noticing, because pinning the source code didn't pin the container images. Two imports also failed quietly. The dynamic scan parser only accepted XML, and the Kubernetes scan, sent to the parser its name suggests, imported successfully with zero findings. A green import with nothing in it is worse than an error. I pinned the images, converted the existing report without re-scanning, imported the Kubernetes report with the parser that understands it, and deleted the empty tests so they couldn't be mistaken for clean results.

The number I would put on a slide is this: **852 rows, about 375 real issues, and one confirmed exploitable bug class**. The 852 is what the tools produce. The gap to 375 is the same vulnerability reported by different scanners, by the same scanner twice, and by an init container that runs the same image. Without deduplication and an honest look at which issues are real, a team spends the week on the wrong number. With it, the plan is clear: fix the injection first, then the fifteen critical dependency vulnerabilities that already have a fix. Everything else gets a deadline, an owner, and in one case a documented risk acceptance with a compensating control and an expiry date.

A security tool is only as useful as the decision it supports, and every tool here earned its place that way.
