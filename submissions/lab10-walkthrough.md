# Lab 10 Bonus — The five-minute walkthrough

*("Tell me about a security project you've worked on.")*

Throughout a semester-long DevSecOps course, I took one intentionally vulnerable application — OWASP Juice Shop — and built the surrounding security pipeline you would expect for a real-world service: dependency scanning, SAST, DAST, infrastructure-as-code scanning, container and Kubernetes hardening, supply-chain signing, and runtime detection. The goal wasn't simply to put eleven security tools on my resume. I wanted to understand what each tool could detect that the others could not, and then combine the results from all nine weeks into a single system rather than leaving them as nine disconnected sets of results that nobody would realistically review.

Let me describe one finding that I followed from detection all the way to the underlying cause. During the DAST lab, I performed an authenticated OWASP ZAP scan against Juice Shop. ZAP reported a High-severity SQL Injection issue on the product search endpoint — `GET /rest/products/search?q=...`. The evidence ZAP provided was an HTTP 500 response after inserting a single quote into the query parameter. That is a useful indicator, but by itself it does not prove SQL injection: the 500 response could simply mean that the application crashed. So I investigated the source code. Juice Shop builds the search query using string concatenation rather than a parameterized query, which is precisely the type of issue that Semgrep's static analysis independently detected in the same lab and the same file, reporting it as an ERROR-severity finding involving unsanitized query construction. Two separate tools approached the application from different directions — one testing the running service externally and the other analyzing its source code internally — yet both identified the same underlying problem. If this were a real vulnerability-triage queue, this would be the finding I would prioritize first. It also illustrates the main lesson that emerged from the capstone: an isolated scanner alert is only one piece of evidence, while an alert independently confirmed by another tool using a different detection method provides much stronger grounds for prioritization.

Now for something that went wrong. When I attempted to import the ZAP scan's JSON report into DefectDojo — the vulnerability-management platform I deployed for the capstone — the import failed with HTTP 400 and the rather unhelpful message "wrong file format, use xml." This was confusing because the lab instructions explicitly required importing the JSON report, and DefectDojo's parser documentation listed "ZAP Scan" as supporting that format. I could have simply skipped the report and accepted the missing data, which would have been an easy way to move on. Instead, I inspected DefectDojo's actual parser implementation rather than relying only on the documentation. The source revealed that the ZAP parser explicitly checks for an `.xml` extension and only processes ZAP's XML report structure. In other words, although JSON is also an official ZAP report format, that particular DefectDojo importer never supported it. Instead of repeating the entire scan just to obtain XML, I created a small conversion script that transformed the exact same alert information — including the titles, CWEs, and evidence — from the JSON structure into the XML structure expected by the parser. I then imported the converted report successfully. The result was the same thirteen findings with no information lost; only the representation had changed.

I encountered almost the same issue again with the Kubernetes Trivy scan. The lab instructed me to import it using "Trivy Operator Scan," but that parser expects the schema generated by a running Kubernetes Trivy Operator rather than the standard CLI JSON produced by `trivy k8s`. The file was accepted without an error, but DefectDojo showed zero findings. I discovered the problem because I compared that result with the findings I could independently verify in the original report. The solution was to recognize that the regular "Trivy Scan" parser already contained a code path for the exact CLI schema I had. These two incidents led to the same conclusion: a successful import does not necessarily mean that the data was processed correctly. When an integration silently produces an incorrect result, the quickest way to understand what happened can be to inspect the parser implementation itself rather than trusting the integration or mapping documentation.

If I had to put a single number on a presentation slide, it would be this: **645 active findings, but roughly 79% of them are three overlapping dependency scans of the same base container image**. That means the actual, deduplicated risk surface is much smaller than the headline number suggests. The metric that really matters is not simply "how many findings exist," but "how many distinct security problems exist, and which of them are new since last week." That is the number I would want to display on a dashboard, rather than the raw finding count, because counting the same underlying issue across three different scans inflates the total without providing additional insight.
