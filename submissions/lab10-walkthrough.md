# Lab 10 Walkthrough — Five-minute security project story

The project I worked on was a DevSecOps security program for the OWASP Juice Shop application. The goal was to move security checks from isolated exercises into a delivery process that could prevent insecure changes, explain risk, and detect problems after deployment.

I started by defining the application and its data flows. I modeled the technical assets and trust boundaries, then used the model to identify risks around the web application, database, authentication, and administrative interfaces. That gave the later scanner results a context: a vulnerable library, an exposed network path, and an over-privileged identity were connected to real application assets instead of being anonymous rows in a report.

I built the software supply-chain checks next. I generated a CycloneDX software bill of materials, scanned it for vulnerable components, and added static and dynamic testing. The important design choice was to treat scan output as a build input. A release was useful only when the image, source checks, runtime configuration, and dependency inventory could be traced to the same version.

One finding I traced end to end was an infrastructure issue from the intentionally vulnerable Terraform configuration: an IAM policy allowed excessive permissions. Checkov reported the policy, KICS provided a second policy-as-code view, and the finding pointed to the specific resource and line in `iam.tf`. I changed the policy to least privilege by removing wildcard permissions and adding action and resource constraints. I reran the scanner and used the clean result as the verification evidence. The lesson was that a finding is not finished when it is acknowledged; it is finished when the changed artifact produces a passing control result.

I then hardened the container and Kubernetes deployment. The image ran as a non-root user, dropped Linux capabilities, disabled privilege escalation, used a read-only root filesystem, pinned the image, and declared resource limits and probes. Trivy tested both the image and Kubernetes manifests. I also signed the image by digest and attached an SBOM and provenance attestation. That made the release identity explicit: a mutable tag was not enough to establish what had been approved.

Runtime and admission controls covered a different failure mode. Falco detected a shell attached to a running container, access to `/etc/shadow`, and writes below `/tmp`. I added the `/tmp` rule because it detects runtime drift that a static manifest cannot predict. Conftest enforced similar expectations before Kubernetes deployment. The two controls complement each other: admission prevents known-bad configuration, while runtime detection identifies activity that appears after deployment or comes from a compromised process.

One thing did not work exactly as written. The Falco setup expected Linux host mounts, including `/boot`, but Docker Desktop on macOS rejected the `/boot` bind mount. Falco also reported missing LinuxKit tracepoints for part of its TOCTOU mitigation. I adapted by running Falco without the unavailable `/boot` mount, confirmed that the service loaded the rules, and verified the shell, sensitive-file, and `/tmp`-write alerts. I recorded the kernel limitation and marked the synthetic cryptominer alert for validation on a Linux VM or Colima environment with the required tracepoints. The important response was to separate a platform limitation from a broken rule and preserve the evidence of both.

At the capstone stage I imported the available Checkov, KICS, and Trivy outputs into DefectDojo 2.58.3. DefectDojo combined the results into one product and engagement, exposed duplicate titles for investigation, and applied deadlines. I changed the SLA to three days for critical findings, fourteen for high, forty-five for medium, and ninety for low. I would not use the dashboard as a vanity count: each critical and high finding needs an owner, a remediation decision, and a verification artifact.

The number I would put on the slide is **183 active findings**, including **12 critical and 87 high**. That number is the current imported baseline, not a claim that every issue has equal risk. The next slide would show the owners and deadlines for the critical/high set, the image rebuild plan, the infrastructure fixes, and the missing Lab 4–5 coverage that must be restored before calling the program complete.
