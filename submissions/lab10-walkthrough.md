# Five-minute walkthrough: "Tell me about a security project you worked on"

*Spoken script, about 700 words.*

---

Over one semester I took a single application, OWASP Juice Shop, and built a security programme around it step by step: from a threat model to a dashboard where every finding has a severity, an owner and a deadline. Juice Shop is deliberately vulnerable, which was the point: the hard part was never finding problems, it was deciding which ones mattered.

I started on the left. I modelled the deployment with STRIDE in Threagile and measured how much risk the hardened version actually removed, rather than assuming it did. I made every commit SSH-signed and put gitleaks in a pre-commit hook, because a secret caught on my laptop costs nothing and one caught in history costs a rewrite. Then I scanned the build from four angles. For dependencies I generated an SBOM once and scanned the SBOM with Grype, and the image with Trivy, so that when a new CVE comes out I can answer "did we ship it?" without rebuilding anything. I used Semgrep for the code and ZAP, authenticated, against the running app. I ran Checkov and KICS on the infrastructure code. After that I hardened the Kubernetes deployment, signed the image and its SBOM with Cosign, and added Falco at runtime, with Conftest enforcing the same rules before deploy.

The finding I would pick is SQL injection, because two tools that know nothing about each other agreed on it. ZAP reported an injection on `GET /rest/products/search` with the payload `'(`, and a second one on the login endpoint. Separately, Semgrep flagged `routes/search.ts`, line 23, where the search term is pasted into the SQL string with a template literal: `LIKE '%${criteria}%'`. Same endpoint, same line, one from watching the app and one from reading it. That is how I triage: a static hit confirmed by a dynamic one goes straight to the top. Semgrep also flagged four more files with the same rule, but they turned out to be Juice Shop's challenge answer snippets that are never executed, so I recorded them as false positives instead of creating four tickets. The fix is small: pass the term as a bound parameter, using Sequelize's `replacements` with `:criteria`, instead of building the SQL string by hand. Then the proof is to re-run the authenticated ZAP scan, not to trust the diff. The login query gets the same treatment.

Something that did not work: the runtime part. Falco, at the version the course specified, started without errors on my machine and then reported nothing at all, not even its own built-in alerts. Instead of tweaking rules, I checked whether it was receiving events. It had used one second of CPU in fourteen minutes, and its main thread was stuck in the kernel, in `register_kprobe`, in an unkillable state. So the problem was an incompatibility between that Falco version's eBPF probe and the WSL2 kernel, not my rules. I switched to an older release that attaches in ten seconds, and I documented the deviation and the evidence instead of hiding it. Once Falco was working I found a second, subtler problem: my cryptominer rule did not fire on a refused connection, because a failed `connect()` carries no socket data, only the address the process asked for. I rewrote the rule to match the requested address. The lesson I took is to check that the sensor works before trusting its silence.

Finally I pulled everything into DefectDojo. Four of the nine imports failed at first, each for a different reason: a wrong file encoding, a parser that only reads XML, a timezone, and one that "succeeded" with zero findings. That last one taught me to check the numbers that come back, not just the HTTP status. I also set deadlines I can defend, three days for critical and two weeks for high, which dropped SLA compliance from 98 to 86 percent. That is the honest number, because nothing had been fixed; the old defaults simply hid it.

The number I would put on the slide is **804 to 377**. The scanners produced 804 findings. Deduplication and correlation bring that down to about 377 real problems, and roughly a dozen of those are this sprint's work. A security programme, as I see it now, is the process that turns the first number into the second, and then makes the second one go down.
