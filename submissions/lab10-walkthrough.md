# Five-Minute Walkthrough — "Tell me about a security project you've worked on"

Over ten weeks I built a working DevSecOps pipeline around one deliberately vulnerable target, OWASP Juice Shop, adding one defensive layer each week and ending with every finding in a single vulnerability-management system. The point wasn't to collect tools — it was to get from "we scanned some things" to "we know what to fix first and when it's due."

I'll start with the shape. I ran the app, threat-modelled it with STRIDE in Threagile, then locked down my own supply chain: SSH-signed commits and a gitleaks pre-commit hook so secrets can't leave the laptop. From there the pipeline reads the software from the outside in — an SBOM with Syft and a CVE scan with Grype; SAST with Semgrep and DAST with ZAP against the running app; infrastructure-as-code scanning with Checkov and KICS; a container and Kubernetes pass with Trivy under the restricted Pod Security Standard; image signing and SBOM attestation with Cosign; runtime detection with Falco; and finally everything imported into DefectDojo for triage. Each tool earned its place: Grype because the SBOM becomes a signable artifact I can re-scan in seconds when the next CVE drops, ZAP because a scanner that only reads code never sees the request that actually breaks the app, Cosign because a tag is a mutable pointer and only a digest signature survives someone swapping the image.

Let me trace one finding end to end, because that's the part that matters. Semgrep flagged `routes/search.ts`: a product-search query built by string interpolation — `...name LIKE '%${criteria}%'...` straight from the request. On its own that's a static warning. But in the same week ZAP, attacking the running container, sent `q='(` to `/rest/products/search` and got an HTTP 500 — the database engine choking on a broken query. Two tools, two directions, same line of code: that's a confirmed SQL injection, not a maybe. The fix was a parameterised query with bound replacements so the input is data, never SQL. When I imported both scanners into DefectDojo it showed up from each — which is exactly the kind of thing a vulnerability-management system is supposed to reconcile.

Now the thing that didn't work, because every real project has one. When I loaded the ZAP report into DefectDojo, the import failed: `Wrong file format, please use xml`. DefectDojo's ZAP parser only reads ZAP's XML, and I'd generated JSON. Rather than hand-wave it, I re-ran the authenticated scan with an XML report job and imported that cleanly. The broader lesson showed up at the same time: DefectDojo had no parser at all for my Cosign signatures or my Falco runtime alerts, so those controls were invisible to the finding count. I learned to treat "which parser, which format" as a design decision up front, and to track signing and runtime detection as separate controls rather than pretending the CVE count covers them.

That leads to the number I'd put on a slide. The dashboard said 577 active findings — and I'd immediately explain why that's almost the wrong number. Roughly 142 CVEs were the same packages reported by both Grype and Trivy, counted twice; a chunk more were base-OS CVEs with no fix available, and some Semgrep hits were in the project's own teaching snippets. The honest headline isn't "577 problems." It's "one confirmed, exploitable SQL injection, a handful of Critical dependency bumps that are one-line fixes, and one wildcard IAM policy — closeable in a single developer-sprint." So the number I actually present is a governed one: I changed DefectDojo's SLAs to 3 days for Critical and 14 for High, and the story is "here's what's past due and who owns it," not a raw total.

If I had to compress the whole semester to one sentence: I can take nine different scanners' output, collapse the duplicates, decide the deadlines, and tell you the two or three things worth doing this week — which is the difference between security theatre and a program.
