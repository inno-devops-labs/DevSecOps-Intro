**Two parser mismatches I had to work around, not covered by the lab's pitfalls list:**

1. **`run-imports.sh` failed on `auth-report.json` → `ZAP Scan` with `HTTP 400: "Internal error: Wrong file format, please use xml."`** I inspected DefectDojo's parser implementation directly (`dojo/tools/zap/parser.py:76-78`) and found that it explicitly requires `file.name.endswith(".xml")` and processes `<site><alerts><alertitem>` XML elements. It does not support ZAP's JSON report format, even though JSON and XML are both official ZAP output formats and the lab's own file/parser mapping pairs `auth-report.json` with `ZAP Scan`. I therefore created a small conversion script (`labs/lab10/work/zap_json_to_xml.py`) that transformed the same alert information — title, description, riskcode, cweid, solution, reference, and instances — from the JSON representation into the XML structure expected by the parser. I then manually imported the resulting `auth-report.xml`. The import contained the same 13 findings with the same severities; only the outer report format was changed.

2. **`trivy-k8s.json` imported as `Trivy Operator Scan` (per the lab's table) produced 0 findings, silently.** I inspected `dojo/tools/trivy_operator/parser.py` and found that it expects the Kubernetes CRD format generated by Trivy Operator, using `metadata.labels` and `report.vulnerabilities` for each resource. The `trivy-k8s.json` file generated by `trivy k8s ... --format json` in Lab 7 instead uses a different plain-CLI JSON structure containing top-level `ClusterName` and `Resources[].Results[].Vulnerabilities`. Because `metadata` is missing, the parser's `output_findings()` immediately returns `[]` without reporting an error. I then inspected `dojo/tools/trivy/parser.py:176-230`, where the parser explicitly handles `cluster_name = data.get("ClusterName")` and iterates through `Resources[].Results[]`. This confirmed that the regular `Trivy Scan` parser is the appropriate parser for this report. Re-importing it as `Trivy Scan` resulted in 77 findings (74 verified vulnerabilities plus misconfiguration entries), consistent with the 74 vulnerabilities I independently counted in the raw JSON using `jq`. I removed the two empty or incorrectly routed test records (ZAP-as-JSON and Trivy-Operator), leaving only the nine correctly imported tests in the instance.

**Two duplicate titles:**

1. **`CVE-2015-9235 Jsonwebtoken 0.1.0`** — occurs three times (finding IDs 261, 499, 589), in tests 2 (`Trivy Scan`, Lab 4's `trivy.json`), 8 (`Trivy Scan`, Lab 7's `trivy-image.json`), and 11 (`Trivy Scan`, Lab 7's `trivy-k8s.json`). I compared `component_name`, `component_version`, and `file_path` for all three records and found them identical (`jsonwebtoken` 0.1.0 and the same `node_modules/express-jwt/node_modules/jsonwebtoken/package.json` path). **These three records therefore represent one underlying vulnerability appearing three times**, because Labs 4 and 7 scanned the same Juice Shop image, or a container derived from it, with the same scanner at different stages of the course. DefectDojo's `duplicate` flag was `false` for each record. Cross-test and cross-engagement deduplication is not automatic under the way these imports were performed; it requires product-level deduplication configuration or importing into the same test.

2. **`CVE-2020-8203 lodash.set 4.3.2`** — follows the same pattern, with three occurrences (IDs 278, 510, 600) sharing the same component/version and appearing in tests 2/8/11. The conclusion is the same: this is one underlying vulnerability represented three times because several labs scanned overlapping targets. I determined this by comparing `component_name` + `component_version` + `file_path`, rather than relying only on the title. In this case, the title (`CVE-xxxx Component Version`) is already sufficiently specific that a matching title combined with matching component and path is strong evidence of duplication rather than coincidence.

Importantly, **Grype and Trivy never generate identical titles for the same vulnerability**, even when they identify the same CVE in the same package. For example, Grype may report `CVE-2010-4756 in libc6:2.41-12+deb13u2`, while Trivy may produce `CVE-2015-9235 Jsonwebtoken 0.1.0`; their title formats are different. As a result, the total of 645 almost certainly **understates** cross-tool duplication. A title-based view in DefectDojo cannot expose a Grype/Trivy pair referring to the same CVE, meaning the true number of distinct vulnerabilities is lower than 645 rather than higher.

### Three numbers

**Median age of active findings: 0 days.** **Oldest active finding: 0 days.** I queried `GET /api/v2/findings/?active=true&limit=1000` and then ran `jq '[.[].age]'` on the result. All 645 active records show `"age": 0` and `"date": "2026-10-08"`. This is expected rather than a data-quality problem. By default, DefectDojo assigns a finding's `date` when it is imported; these parsers do not backdate findings based on timestamps contained in the original reports. Although the nine source reports cover scans performed during Labs 4 through 7, with source-file modification dates ranging from September 10 to September 27, they were all imported into DefectDojo for the first time today. Therefore, the accurate interpretation is that today is the first day these results have existed as a centrally tracked and deduplicated vulnerability-management dataset. There is no historical finding-age information because before this capstone there was no continuous vulnerability-management system, only nine separate scans.

**Share of active findings currently inside SLA: 100%** (628 of 628 findings that have an SLA configured — the 17 Info findings have no SLA days set, as shown by `sla_days_remaining: null` — have `sla_days_remaining >= 0`). I calculated this with `jq '[.[] | select(.sla_days_remaining != null)] | length as $t | [.[] | select(.sla_days_remaining >= 0)] | length as $ok | ($ok/$t)*100'` against the same findings dump. The 100% figure is expected for the same reason that all finding ages are zero: the SLA timers only started today. It should therefore not be interpreted as evidence that the vulnerability-management process is already healthy. It means that the clock has only just begun. The same query should be repeated after a week to identify the first genuine SLA breaches.

### What Labs 8 and 9 don't show up in any of these numbers

Lab 8's Cosign verification results — including successful image-signature verification, detection of the tampered image, and two SBOM/provenance attestations — and Lab 9's runtime security results — including Falco's built-in and custom alerts and Conftest's Kubernetes policy results — produced meaningful security evidence. However, DefectDojo 2.58.3 has no parser for these formats. There is no importer for "supply-chain attestation" or a "Falco alert stream," so both a successfully signed image and a live CRITICAL alert generated after a SIGHUP reload contribute zero records to this dashboard.

My immediate solution would be to represent these events as manually created DefectDojo findings, since the API supports `POST /api/v2/findings/` without requiring an import, and tag them according to their source. This would at least bring them into the same inventory. Longer term, I would either implement a small custom DefectDojo parser for Falco's JSON alert format, which is relatively straightforward because the format contains one alert per line, or forward Falco alerts to a SIEM and integrate DefectDojo with an aggregated view of those events.

### Executive summary

Nine weeks of separate scanner results have now been consolidated into a single figure: 645 active findings across nine imported reports, including 45 Critical and 309 High findings that require attention. However, approximately 79% of the total consists of dependency CVEs appearing across three overlapping scans of the same Juice Shop base image rather than 645 separate problems.

The most important limitation is that this is the first day of centralized tracking. Every finding has an age of zero, and the nominal SLA compliance rate is 100% not because remediation is happening quickly, but because none of the findings has existed long enough to become overdue. In addition, two complete labs' worth of security evidence — Cosign attestations and Falco runtime alerts — are absent from the dashboard because DefectDojo does not provide parsers for those formats.

To improve the system, I would first perform proper deduplication across the overlapping Grype and Trivy findings, then decide whether scanning the same base image three times per cycle is actually useful. Finally, I would establish either a custom parser or a manual-finding process for the Lab 8 and Lab 9 evidence so that those results are represented alongside the other security data instead of disappearing from the metric a manager is most likely to see.

The most difficult part of the semester to summarize accurately was the vulnerability-management capstone. The earlier labs each have a straightforward narrative: one tool produces a measurable result, and a remediation changes that result. Lab 10 is different because its purpose is to demonstrate what happens when nine independent, one-off scans are turned into a single searchable system with deduplication and SLAs. That is primarily a process and decision-making outcome rather than a simple technical result, which makes it much harder to reduce to "I ran X and it found Y."

For the next project, I would therefore document the **decision points** while the work is happening: why a particular SLA was selected, which findings were classified as noise, and which were treated as meaningful signals. Reconstructing those decisions afterward from raw finding counts is much harder, because the numbers themselves do not capture the judgment that made the vulnerability-management system useful.
