# Lab 8 — Supply Chain Signing, Tampering, and Attestation

I signed a Juice Shop image in a local registry, replaced its tag with Alpine,
and checked which digest still passed verification. I also attached and verified
two attestations, then repeated the tampering test with a signed release archive.
Both tampering tests failed as expected; the original image and archive passed.

## Environment and reproducibility

| Item | Version or reference |
|---|---|
| Run date | 27 September 2026 |
| Host | Windows, PowerShell; Python used to capture output and decode JSON |
| Docker client / server | 29.2.1 / 29.2.1 |
| Cosign | v3.0.2, Windows/amd64 |
| Registry | `registry:3`, bound to `127.0.0.1:5000` |
| Application | Juice Shop v20.0.0, Linux/amd64 |
| SBOM input | CycloneDX generated by Syft 1.52.0; 3069 components |

The branch starts at `main` and adds only this report and the
[public verification key](../labs/lab8/keys/cosign.pub). The required existing
SBOM was used as a local input at `labs/lab8/results/juice-shop.cdx.json`.
Raw outputs, decoded statements, archives, and the encrypted private key remain
local and ignored by Git. The passphrase is stored locally using Windows DPAPI
and is supplied to Cosign through the process environment, never as a command-line
argument or in this report.

Two adjustments were needed on this installation:

- Docker pushed only the available Linux/amd64 manifest. Immediately after the
  push, local `RepoDigests` still named the source's multi-platform index.
  Pulling the local tag refreshed that metadata; I then filtered by registry
  prefix and cross-checked the result with `docker buildx imagetools inspect`.
- Cosign's default signing configuration attempted a Rekor upload despite
  `--tlog-upload=false`. That first attempt published a signature over the
  upstream index digest and the public key, then failed because that index was
  absent from the local registry. No private key was uploaded. The successful
  image and attestation commands below explicitly disable that configuration
  and use the legacy format; blob signing disables the configuration while
  retaining its bundle format. Subsequent signing logs showed no Rekor upload.

These are local, key-based tests. The transparency-log bypass flags below are
part of this lab setup, not a template for keyless CI signing.

## Task 1

### Publish and select the digest

I started the registry and copied the pinned source image:

```powershell
docker run -d --name lab8-registry -p 127.0.0.1:5000:5000 registry:3
docker tag bkimminich/juice-shop@sha256:fd58bdc9745416afce8184ee0666278a436574633ea7880365153a63bfd418b0 localhost:5000/juice-shop:v20.0.0
docker push localhost:5000/juice-shop:v20.0.0
docker pull localhost:5000/juice-shop:v20.0.0
$DIGEST = docker inspect localhost:5000/juice-shop:v20.0.0 --format '{{range .RepoDigests}}{{println .}}{{end}}' |
  Where-Object { $_ -like 'localhost:5000/*' }
$DIGEST | Set-Content labs/lab8/results/juice-shop-digest.txt
docker buildx imagetools inspect localhost:5000/juice-shop:v20.0.0
```

The signed reference was:

```text
localhost:5000/juice-shop@sha256:28870b9d2bec49e605d6ebbf4b22ed1ec1ca0a72347ef19217bbbb21ea44e3fe
```

I selected the `localhost:5000/` entry rather than assuming entry zero belonged
to the local registry. The push output and registry inspection both reported
`sha256:28870b9d2bec49e605d6ebbf4b22ed1ec1ca0a72347ef19217bbbb21ea44e3fe`.
Inspecting the upstream index `sha256:fd58bdc9745416afce8184ee0666278a436574633ea7880365153a63bfd418b0`
confirmed that this is its Linux/amd64 child manifest, the platform covered by
the input SBOM. The differing digests describe an index and its child manifest,
not two different application builds.

### Generate the key and verify the signature

```powershell
cosign generate-key-pair --output-key-prefix labs/lab8/keys/cosign
git add labs/lab8/keys/cosign.key
```

The private-key staging attempt exited with code **1**:

```text
The following paths are ignored by one of your .gitignore files:
labs/lab8/keys/cosign.key
hint: Use -f if you really want to add them.
hint: Disable this message with "git config advice.addIgnoredFile false"
```

On this clean branch, `.gitignore` rejected the file before staging. This is
an ignore-rule check, not evidence that a pre-commit hook ran. I did not use
`git add -f`; only the public key is included in the submission.

With `COSIGN_PASSWORD` set for the signing process:

```powershell
cosign sign --key labs/lab8/keys/cosign.key --tlog-upload=false `
  --use-signing-config=false --new-bundle-format=false `
  --allow-insecure-registry --yes $DIGEST
cosign verify --key labs/lab8/keys/cosign.pub --insecure-ignore-tlog `
  --allow-insecure-registry $DIGEST
```

Both commands exited with code **0**. Successful verification printed:

```text
WARNING: Skipping tlog verification is an insecure practice that lacks transparency and auditability verification for the signature.

Verification for localhost:5000/juice-shop@sha256:28870b9d2bec49e605d6ebbf4b22ed1ec1ca0a72347ef19217bbbb21ea44e3fe --
The following checks were performed on each of these signatures:
  - The cosign claims were validated
  - The signatures were verified against the specified public key
```

Its JSON output was:

```json
[{"critical":{"identity":{"docker-reference":"localhost:5000/juice-shop"},"image":{"docker-manifest-digest":"sha256:28870b9d2bec49e605d6ebbf4b22ed1ec1ca0a72347ef19217bbbb21ea44e3fe"},"type":"cosign container image signature"},"optional":null}]
```

### Replace the tag and verify again

```powershell
docker pull alpine:3.20
docker tag alpine:3.20 localhost:5000/juice-shop:v20.0.0
docker push localhost:5000/juice-shop:v20.0.0
docker pull localhost:5000/juice-shop:v20.0.0
$TAMPERED = docker inspect localhost:5000/juice-shop:v20.0.0 --format '{{range .RepoDigests}}{{println .}}{{end}}' |
  Where-Object { $_ -like 'localhost:5000/*' }
cosign verify --key labs/lab8/keys/cosign.pub --insecure-ignore-tlog `
  --allow-insecure-registry $TAMPERED
```

The unchanged tag now resolved to:

```text
localhost:5000/juice-shop@sha256:c64c687cbea9300178b30c95835354e34c4e4febc4badfe27102879de0483b5e
```

Verification exited with code **10**. Exact stderr:

```text
WARNING: Skipping tlog verification is an insecure practice that lacks transparency and auditability verification for the signature.
Error: no signatures found
error during command execution: no signatures found
```

I then reran verification against `$DIGEST`, without restoring the tag. It exited
with code **0**, validated the claims and public-key signature again, and returned:

```json
[{"critical":{"identity":{"docker-reference":"localhost:5000/juice-shop"},"image":{"docker-manifest-digest":"sha256:28870b9d2bec49e605d6ebbf4b22ed1ec1ca0a72347ef19217bbbb21ea44e3fe"},"type":"cosign container image signature"},"optional":null}]
```

The signature authenticates the image's manifest digest under the supplied
public key; the signed payload also records the repository identity.
Changing `v20.0.0` changed which digest the tag selected, but did not give the
replacement image a valid signature. The original digest still verified because
its content and signature had not changed. If a signature authenticated only
the tag text, an attacker could move that tag to different content and reuse
the same apparent approval.

## Task 2

### Attach and recover the SBOM

I attached the SBOM to `$DIGEST`, the original Juice Shop manifest, while the tag
still pointed to Alpine:

```powershell
cosign attest --key labs/lab8/keys/cosign.key --type cyclonedx `
  --predicate labs/lab8/results/juice-shop.cdx.json `
  --tlog-upload=false --use-signing-config=false --new-bundle-format=false `
  --allow-insecure-registry --yes $DIGEST
cosign verify-attestation --key labs/lab8/keys/cosign.pub `
  --insecure-ignore-tlog --allow-insecure-registry --type cyclonedx $DIGEST
```

Both commands exited with code **0**. I decoded the `payload` field from the
verified JSON envelope, parsed the resulting statement, and saved its `predicate`:

```python
envelope = json.loads(verified_stdout)
statement = json.loads(base64.b64decode(envelope["payload"]))
extracted = statement["predicate"]
assert extracted == original_sbom
```

| Check | Result |
|---|---:|
| Input SBOM `components` length | 3069 |
| Verified, extracted SBOM `components` length | 3069 |
| Full parsed JSON equality | True |

Input SBOM file SHA-256:
`5b48aeef336a4bfc26540443a07d01e7dacbc4a9d5ce65293f23bd1c459bf93b`.
I compared the full parsed objects as well as the counts, so the check covers
every component field and the rest of the predicate, independent of formatting.

Provenance statement:

```json
  "_type": "https://in-toto.io/Statement/v0.1",
  "predicateType": "https://slsa.dev/provenance/v0.2",
  "subject": [
    {
      "name": "localhost:5000/juice-shop",
      "digest": {

      }
    }

```

| Field | Where it came from |
|---|---|
| `predicate` | I supplied the SBOM or the three-field provenance body as a JSON file. |
| `_type` | Cosign generated the in-toto statement wrapper. |
| `subject.name` and `subject.digest.sha256` | Cosign filled these from the original digest-qualified image reference I passed. |
| `predicateType` | I selected `cyclonedx` or `slsaprovenance`; Cosign mapped that flag to the URI shown in the verified payload. |

After another Log4Shell, these attestations would let us search the inventories
of 2,000 images for the affected package and version, then identify the exact
image digests to investigate or replace. A plain image signature authenticates
content but provides no package inventory to search. For that to work at
3 a.m., the attestations must be retained and searchable, their signatures
checked against trusted keys, and their subjects matched to the deployed digests.
The SBOMs must also accurately cover the deployed contents: a valid signature
alone cannot establish completeness or freedom from vulnerabilities.

## Bonus

### Sign an archive, then change its contents

I created `install.sh` with this content and packaged it as `my-tool.tar.gz`
using Python's `tarfile` module on Windows:

```bash
#!/bin/bash
echo "installing my-tool"
```

```powershell
cosign sign-blob --key labs/lab8/keys/cosign.key --yes `
  --tlog-upload=false --use-signing-config=false `
  --bundle labs/lab8/results/my-tool.tar.gz.bundle labs/lab8/results/my-tool.tar.gz

  --bundle labs/lab8/results/my-tool.tar.gz.bundle --insecure-ignore-tlog `
  labs/lab8/results/my-tool.tar.gz
```

Signing and verification both exited with code **0**. Exact verification stderr:

```text
Verified OK
```

### What the consumer needs

In addition to the artifact, a consumer needs **`my-tool.tar.gz.bundle`** and
a **trusted `cosign.pub`**. The bundle may be downloaded from the same CDN as
the artifact: changing either cannot create a valid signature under the pinned
key. The public key must already be trusted through an independent,
authenticated channel or pinned in the consumer's configuration; simply
downloading a replacement key from that same compromised CDN defeats the check.

For this key-based, offline-bundle example, I would publish these Bash install
instructions, with Cosign installed and the key already provisioned at the
shown trusted path. The example release domain is a placeholder, not a live
download endpoint:

```bash
set -eu
work=$(mktemp -d)
trap 'rm -rf "$work"' EXIT
cd "$work"
release='https://downloads.example.com/my-tool/v1.0.0'
curl --fail --silent --show-error --location "$release/my-tool.tar.gz" -o my-tool.tar.gz
curl --fail --silent --show-error --location "$release/my-tool.tar.gz.bundle" -o my-tool.tar.gz.bundle
cosign verify-blob --key /etc/my-tool/trusted/cosign.pub \
  --bundle my-tool.tar.gz.bundle --insecure-ignore-tlog my-tool.tar.gz
tar -xzf my-tool.tar.gz
bash ./install.sh
```

These instructions download first and require successful verification before
extracting or executing anything. An attacker who changes the CDN's script or
archive without the trusted signing key causes verification to fail and
`set -e` stops installation. The commonly skipped step is establishing and
pinning the trusted key, together with enforcing verification before execution.
This would block the demonstrated content substitution, although signature
verification alone does not prevent replay of an older, legitimately signed release.
