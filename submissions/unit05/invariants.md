# Invariants catalog

An invariant is a falsifiable property that must hold on every applicable path. Each invariant below names its enforcement mechanism, fail-safe behavior, and negative validation.

| ID | Invariant | Mechanism and ADR | If mechanism is unavailable | Negative test | Evidence location | Status before local validation |
|---|---|---|---|---|---|---|
| I-1 | A caller receives record R only when that caller is entitled to R. | Central authorization middleware compares the authenticated caller with the requested record owner; ADR-011. | Fail closed; deny the request rather than bypass authorization. | Authenticate as User A and request User B’s basket or record; expected result is 403 or an equivalent denial. | `evidence/I-1/` | Open until tested; the worked example demonstrates a violation in Juice Shop. |
| I-2 | Only the intended production workflow identity can obtain the deployment token. | Federated identity credential pinned to the repository’s production environment; ADR-014. | No token, no deployment. There is no fallback to a stored long-lived secret. | Request a token from a feature branch or workflow without the production environment; expected result is token exchange rejection. | `evidence/T-07/` | Must be validated against the configured identity. |
| I-3 | No commit reaches the default branch except through a pull request whose required check passes. | GitHub ruleset requiring pull requests and the named status check; block force-push and deletion; ADR-015. | The merge is blocked if the required check is missing or failing. | Attempt a direct push, force-push, and merge with a failing required check; all must be rejected for the corresponding rule. | `evidence/T-02/` | Must be validated on the target repository. |
| I-4 | Application secrets do not appear in source code, logs, or workflow output. | Key Vault references, secret masking, and repository secret scanning/push protection. | A deployment that cannot resolve a required secret fails rather than printing or substituting a secret. | Attempt to commit a harmless canary string classified as a secret by the configured scanner; verify the push is blocked or flagged. | `evidence/` | Configuration-dependent; collect the actual scanner result. |
| I-5 | Administrative endpoints are not reachable by an unauthenticated internet caller. | Separate administrative authorization and, where applicable, private ingress/access restrictions. | Deny access when the identity or network control cannot be evaluated. | Request a known administrative route without credentials from the permitted test environment; expected result is 401/403 or a network denial. | `evidence/` | Must be checked against the actual route inventory. |
| I-6 | The image deployed to production is the image produced by the approved build. | Registry access limited to the trusted CI identity; deploy by immutable digest; ADR-014. | No deployment if the digest is missing or cannot be verified. | Compare the build digest with the deployed image digest; attempt deployment using an unauthorized identity where the lab environment permits. | `evidence/T-07/` | Must be validated if the deployment environment is available. |

## Known violation and remediation

The supplied worked example demonstrates the central authorization defect: a valid login token proves caller identity but does not prove that the caller owns the requested basket. In that example, User A receives User B’s basket, violating I-1. The mitigation is a resource-level entitlement comparison in the shared authorization choke point, plus route coverage checks so a new route cannot bypass the middleware. The violation remains open until the corrected implementation passes both the positive own-record test and the negative cross-user test.

## Assurance limitations

A passing test covers only the exercised route, identity, and configuration. It does not prove every route is mediated, every role assignment is least-privileged, or every deployment uses the expected digest. Re-run tests after route, identity, workflow, or infrastructure changes. The owner is the repository/application maintainer; review the invariants at each architecture change and at least monthly.
